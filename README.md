# 老地图图幅编目与地名对照台

面向古地图整理者和地方志研究者，将老地图按图幅编目，登记年代、比例尺、投影和扫描件，并建立古今地名对照及沿革线索。应用为纯前端单页程序，所有资料保存在浏览器本地。

## Docker 一键启动

```bash
cp .env.example .env && docker compose up -d --build
```

服务默认映射到宿主端口 `21805`。停止服务可执行：

```bash
docker compose down
```

## 数据存储说明

应用使用 IndexedDB 持久化数据，Dexie 数据库名为 `gboldmap-db`。对象仓库共七个：`sheets`、`scans`、`placePairs`、`histories` 四个主档仓库，以及 `commits`（按图幅提交的操作记录）、`conflicts`（待核台）、`drafts`（未提交草稿）。

写入采用“先记操作记录、再重放主档”的按图幅提交模型：

- `version(1)` 建立首版索引结构，并在首次创建数据库时写入图幅、扫描件、地名对照和沿革种子数据。
- `version(2)` 保持现有索引并对已有图幅执行 `schemaRev = 2` 的回填迁移，用于演示后续结构升级路径。
- `version(3)` 新增提交、待核与草稿三个仓库；升级事务会把升级前的主档记录（图幅、扫描件、地名、沿革）按图幅重放为每个图幅的**首个提交点（建账提交，seq=1）**，主档行版本 `rowRev` 统一置 1。全新建库时种子数据也以同样方式建账。

### 双页签协作与冲突处理

整理员常同时开两个页签处理同一图幅。为避免“最后保存的人覆盖另一边”，所有改动都按图幅生成提交：

1. 写入先进入 `commits` 操作记录，并在同一个 IndexedDB 事务内按序重放到四个主档仓库；记录与主档同落或同不落。
2. 每条操作带实体行版本 `rowRev`。两个页签同时提交时：互不相关的改动（如一边改图幅四至、一边补扫描件）都保留并先后重放；基于旧行版本改到同一条记录的操作进 `conflicts` 待核台，主档对应内容停在**上一提交点**。
3. 互相依赖的改动（如切换主用件会同时改写两件扫描件、沿革依赖地名卡）任一条撞车则整组挂起，不会只落一半，也不会产生没有地名归属的沿革孤记录。
4. 写入失败（例如该图幅已在另一页签推进了提交点）时事务整体回滚，应用自动从磁盘重载到上一提交点，错误提示后可在保留的草稿上重试。
5. 待核内容在“待核台”裁定：可按原内容采纳（作为新提交重放）、采纳前修订，或维持上一提交点（记录归档但不重放）。裁定历史不删除。
6. 表单输入经防抖自动写入 `drafts`，关闭或重开页签后自动恢复未提交内容继续处理。
7. 一个页签落提交后，通过本地存储信号通知其他页签对齐新提交点并重载主档，避免继续以旧基点覆盖。

刷新或关闭页面不会丢失新增记录；浏览器站点数据被清除时会重新触发首次种子数据写入。

可执行 `cd frontend && npm run test:commits` 运行上述提交、并发冲突、依赖挂起与回滚语义的集成验证（基于 fake-indexeddb，共 26 项断言）。

## 核心功能与路由表

| 路由 | 核心功能 |
| --- | --- |
| `/sheets` | 按年代、比例尺和状态筛选图幅，内联新建图幅，查看扫描件数、地名数与邻接缺编提示 |
| `/sheets/:id` | 查看编制摘要、扫描件条目、主用件切换、图内地名检索及 JSON 导出 |
| `/places` | 古今地名双栏对照，按类型和确定度筛选，对古名、今名、异写及图上方位反向查询并高亮 |
| `/places/:id/history` | 按年代排列沿革时间线，新增初置、改名、迁治或废置记录 |
| `/sheets/:id/neighbors` | 按四至排列邻接图幅，显示主用扫描件、缺编提示与拼合预览 |
| `/conflicts` | 待核台：查看双页签撞车步骤，采纳重放、采纳前修订或维持上一提交点 |
| `/`、未匹配路径 | 自动跳转到 `/sheets` |
